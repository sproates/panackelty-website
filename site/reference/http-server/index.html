Create a listener handle

Constructors

Constructors create a server handle. They do not bind a socket; binding happens when you await listen().

create_server

create_server(port: Nat): Server
port
Port from 1 through 65535.

Returns: a new Server bound to 0.0.0.0, all local IPv4 interfaces.

Errors: an invalid port is returned by listen() as Error(ServerError). The constructor itself is synchronous.

Use this when the server should accept connections on every local IPv4 interface. Use the bound constructor for a loopback-only service.

See the complete ordinary server program.

create_bound_server

create_bound_server(address: Str, port: Nat): Server
address
Dotted-decimal IPv4 bind address.
port
Port from 1 through 65535.

Returns: a new Server for that address. For example, "127.0.0.1" accepts connections from the local machine only.

Errors: invalid address and port values are returned by listen() as ServerError. Hostnames and IPv6 addresses are unsupported.

Async: no. The socket is opened later by await server.listen().

See the complete loopback server program.

create_contextual_server

create_contextual_server[T](port: Nat, context: T): ContextualServer[T]
port
Port from 1 through 65535.
context
Typed value stored for this server; its type determines T.

Returns: a contextual server that binds to 0.0.0.0 when listening.

Errors and async: the same port errors as create_server; construction is synchronous.

Each contextual handler receives the stored value as its first parameter. The value's type is inferred from context; all handlers on this server must use the same T. Handlers are named async function references and do not capture closures.

record AppConfig { greeting: Str }

async home(context: AppConfig, request: http.Request,
    response: http.ResponseWriter): Result[Unit,Str] {
  response.send(context.greeting)
  Ok(())
}

server = http.create_contextual_server(8081, AppConfig("Hello"))
server.get("/", @home)

See the complete contextual server program.

create_bound_contextual_server

create_bound_contextual_server[T](address: Str, port: Nat, context: T): ContextualServer[T]
address
Dotted-decimal IPv4 bind address.
port
Port from 1 through 65535.
context
Typed value stored for this server; its type determines T.

Returns: a contextual server using the specified address. "127.0.0.1" keeps the listener local; "0.0.0.0" listens on all local IPv4 interfaces.

Errors and async: invalid address and port errors are returned by listen(); construction is synchronous. Hostnames and IPv6 are unsupported.

See the complete contextual example source, which binds to loopback and shares a typed greeting and query between handlers.

Ordinary handlers

Server route methods

Register exact routes with named async handlers. A matching handler receives a Request and its ResponseWriter; invalid or duplicate routes are reported by listen().

Server.get

get(
  path: Str,
  handler: AsyncFn[
    Request,
    ResponseWriter,
    Result[Unit, Str]
  ]
): Unit
path
Exact URI-reference path beginning with /.
handler
Named async function with the ordinary handler signature.

Returns / async: Unit; registration is synchronous. The handler receives the parsed Request and request-scoped ResponseWriter.

Errors: invalid or duplicate routes become setup errors reported by listen(). Registering after listening begins traps.

GET is supported. A missing exact route runs the fallback if one is registered; otherwise the response is 404. Paths match case-sensitively without decoding or normalization.

Async listener lifecycle

Lifecycle methods

These methods are asynchronous on both Server and ContextualServer[T]. Await them and handle their Result.

Server.listen

async listen(): Result[Unit,ServerError]

Returns: Ok(()) when the listener is bound, or Error(ServerError) if setup or binding fails. Inspect error.message for a human-readable explanation; exact wording is not stable.

Lifecycle: resolves when ready, not when the server stops. The active listener keeps a native process alive after main returns. A closed or destroyed server cannot be restarted.

Async: required; call it with await in an async function. The complete ordinary program handles both result cases.

Server.close

async close(): Result[Unit,ServerError]

Returns: Ok(()) when shutdown completes, or Error(ServerError) on an operation failure.

Lifecycle: stops new admissions and drains active handlers and response writes for up to one second, then cancels remaining work and releases resources. It is idempotent. Normal exit and termination signals use bounded cleanup too.

Async: required; call with await. The package integration tests exercise close during active work; the ordinary runnable program demonstrates signal-driven shutdown with Ctrl-C.

Server.destroy

async destroy(): Result[Unit,ServerError]

Returns: Ok(()) when resources are released, or Error(ServerError) on an operation failure.

Lifecycle: stops new admissions and cancels active handlers immediately without the graceful drain. It is idempotent; a destroyed server cannot be restarted.

Async: required; call with await. Destroy is for immediate cancellation; ordinary shutdown uses close().

ContextualServer.listen

async listen(): Result[Unit,ServerError]

Binds the contextual server and resolves when ready. It reports recorded route/address/port setup failures and listener failures as Error(ServerError); read the human-readable message field.

The active listener keeps the native process alive. The server cannot restart after shutdown. Await this method and match both result cases; see the complete contextual program.

ContextualServer.close

async close(): Result[Unit,ServerError]

Stops new admissions, drains active contextual handlers and response writes for up to one second, cancels remaining work and releases resources. It is idempotent and returns Result[Unit,ServerError].

Await this method. Normal process exit and termination signals use bounded cleanup too. For the ordinary-vs-contextual handler difference, see the contextual constructor.

ContextualServer.destroy

async destroy(): Result[Unit,ServerError]

Stops new admissions, cancels active contextual handlers immediately, and releases resources. It is idempotent and returns Result[Unit,ServerError].

Await this method when immediate cancellation is required. A destroyed server cannot be restarted.

Observable behaviour

Routing, errors and limits

Handler inputs and responses

Request contains method, raw path, raw query without ?, ordered headers, and buffered body bytes. request.header(name) returns the first case-insensitive match; header_values(name) preserves repeated values.

ResponseWriter starts with status 200. Set a status with status, replace a header with header, append a repeated header with add_header, and finish once with send or send_bytes. Text defaults to UTF-8 plain text; bytes default to application/octet-stream. The server owns framing headers and closes each connection after one response.

async echo(request: http.Request,
    response: http.ResponseWriter): Result[Unit,Str] {
  response.send_bytes(request.body)
  Ok(())
}

The complete ordinary program registers GET / and POST /echo; the contextual program demonstrates typed configuration, a query-derived response header and a fallback.

Setup and handler errors

ServerError is a public record with message: Str. Messages are for people, not stable machine-readable codes. Invalid route references, duplicate method/path pairs and duplicate fallbacks are recorded at registration and returned from listen() before binding.

Only GET, POST, PUT and DELETE are supported. Unsupported methods receive 405 and never reach a fallback. A supported method with a different route method on a known path receives 405; an unmatched path receives 404 unless a fallback handles it.

A handler returning Error(message), returning without sending, or trapping with a recoverable request fault is logged and becomes a generic 500 before response commit. A failure after send cannot replace the committed response, and a failed request does not stop healthy requests.

Fixed limits

These first-version bounds are fixed by the implementation; there are no tuning arguments:

  • 16 open connections and 4 admitted requests at once.
  • 16 KiB request headers and 16 KiB response headers.
  • 1 MiB request bodies and 1 MiB response bodies.
  • 10 seconds from connection acceptance through request and response completion.
  • Up to one second to drain active work during close().

Request bodies are buffered before handlers run. Capacity overflow returns 503; oversized request bodies return 413 and oversized request headers return 431. There is no TLS server, WebSocket, HTTP/2, streaming response, keep-alive, route parameters or middleware.
